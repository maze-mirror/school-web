## 1 我们想做一个什么工具

把文件放进来，知道这个项目用了哪些语言、有多少有效代码、哪些文件占得最多；过一段时间再看，能了解项目规模怎样变化。这是代码统计的基本用途。

我们希望数字背后有解释。例如，1000 行里面有多少空行和注释，为什么某个文件没有算进去，历史中的某个数字是哪一天留下来的。页面应该让使用者顺着看明白，而不是只摆出一个很大的总数。

前期讨论里还有一个一直保留的问题：Python 和 C++ 的写法不同，直接比行数公平吗？我们的处理原则是：先把“如何数”说清楚。有效物理行可以描述规模，但不能直接换算成开发难度、学习效果、代码质量或个人贡献。逻辑语句数、重复代码和复杂度将来可以作为补充维度，暂时不设计一个看似精确的“综合代码量分数”。

## 2 开发环境和运行方式

我们把三个网页放在同一个仓库 `school-web` 中。代码统计位于 `apps/code-meter-web`。这样两人可以共用依赖管理和开发约定，也能分别运行三个应用。

| 工具 | 在项目中的作用 | 当前约定 |

Node 在这里主要用于开发和构建。网站的统计工作在浏览器中完成，首版不需要单独搭建 Node 后端或服务器数据库。当前饼图是轻量的页面组件，没有实际使用前期讨论过的 ECharts；以后图表复杂了再考虑引入。

### 2.2 本地怎么运行

在 VS Code 的 PowerShell 终端中，进入仓库根目录：

```powershell
Set-Location D:\Projects\school-web
node --version
pnpm --version
pnpm install --frozen-lockfile
pnpm --filter code-meter-web dev --port 5173 --strictPort
```

随后打开 `http://localhost:5173/`。终端里的 `__devtools__/` 地址是 Vue 调试工具，不是项目首页。运行时终端要保持打开。停止开发服务器使用 `Ctrl+C`；查看 Git 长输出时如果停在 `(END)`，使用 `q` 退出。

`--frozen-lockfile` 用于按现有锁文件安装。如果提示锁文件与依赖配置不一致，应先检查最近是否改过依赖，由一位成员更新并一起提交配置和锁文件，再让另一位同步。

提交前可以在根目录执行：

```powershell
pnpm --filter code-meter-web type-check
pnpm --filter code-meter-web test:unit --run
pnpm --filter code-meter-web build
```

根目录当前的 `test` 命令还是初始化占位内容，暂时不要把直接运行 `pnpm test` 当成项目验收。后续需要补上统一检查入口。

### 2.3 项目文件和使用数据放在哪里

项目代码放在 D 盘。依赖缓存、编辑器数据和浏览器数据的位置由各自工具决定，不会因为项目移到 D 盘就全部一起移动。

扫描快照保存在当前浏览器的 IndexedDB 中，可以理解为“这个网站自己的本地数据柜”。项目名称和主题设置保存在 localStorage 中，适合放少量设置。快照保留统计、文件路径、配置和时间，不保存源代码正文。

换浏览器、清除网站数据或换网址，可能看不到原来的历史；`localhost` 与 `127.0.0.1`、不同端口也属于不同的网站地址。GitHub 保存源代码，不会顺带同步浏览器里的扫描历史。现有 JSON 是报表导出，尚不是可一键恢复全部历史的备份方案。

## 3 基础需求和统计规则

### 3.1 一次完整使用应该是什么样

选择或新建统计档案 → 导入文件或粘贴代码 → 检查语言及排除目录 → 开始统计 → 看总览、语言汇总和文件明细 → 必要时查看历史或导出报表。统计档案是浏览器内保存的记录分组，不会在硬盘创建项目目录；扫描时由用户选择已有本地文件或文件夹。

第一次打开时不放虚构的历史数据。用户可以主动填入示例，体验一次真实的统计。粘贴模式中的“清空”只清除输入，保留已经得到的结果和历史。

### 3.2 每一个数字是什么意思

| 名称 | 用人话解释 | 容易误会的地方 |
| --- | --- | --- |
| 总行数 | 文件中实际存在的物理行 | 文件末尾的一个换行符不额外增加一行 |
| 有效代码行 | 这一行包含代码，或属于跨行字符串内容 | 单独的大括号等也可能算一行；格式会影响数量 |
| 纯注释行 | 这一行只有注释内容 | 多行注释内部的空白行也归入注释 |
| 空行 | 不属于代码或注释内容的空白行 | 多行字符串中的空白行属于字符串内容 |
| 混合行 | 同一行既有代码又有注释 | 它已经包含在有效代码行里，不能再加一次 |
| 语言占比 | 默认使用当前快照；选中某天后使用当天各次已保存扫描累计的有效代码行比例 | 重复扫描也累计；不是开发时间占比或熟练度 |
| 活动方块 | 某一天每次成功保存扫描的有效代码行之和 | 重复扫描也累计；不是新增代码、Git 提交次数或开发工作量 |
| 区间净变化 | 可比较的期末快照减去期初基线 | 不是新增行、删除行或每天工作量的总和 |

基本核对关系是：

```text
总行数 = 有效代码行 + 纯注释行 + 空行
混合行包含在有效代码行里
项目总计 = 成功统计文件的对应数量之和
```

例如，周一有 100 行，周五有 120 行，可以说规模净增加了 20 行；不能把两次扫描相加说成写了 220 行，也不能据此知道中途修改了多少次。

### 3.3 语言细节和能力边界

当前按扩展名识别语言，粘贴文本则由用户选择语言。`.h` 默认按 C 处理。字符串里的 `#`、`//`、`/* */` 不直接当作注释。Python 三引号字符串，包括常见文档字符串，目前计入代码。

**2026-10-28 已确认并接入的新增语言。** Java、JavaScript、TypeScript 沿用物理行口径：一行多条语句仍算一行，单独括号也计代码；字符串内容中的空白计代码，块注释内部的空白计注释，其他空白计空行。同行有代码和注释时归代码，混合行只是代码行子集。

Java 支持 `//`、`/* */`、`/** */` 文档注释、普通字符串／字符及三引号文本块。先处理合法 Unicode 转义的词法含义，再按原始源文件物理行归组；不因转义产生逻辑换行就增加物理行。JavaScript／TypeScript 支持正则、除法、普通字符串、模板字符串及嵌套 `${…}` 插值；插值内按普通代码识别真实注释和空白。TypeScript 类型声明仍计源代码行。

新增文件后缀为 `.java`、`.js/.mjs/.cjs`、`.ts/.mts/.cts`（含 `.d.ts`）。文件导入与文本选择、汇总、图表、历史、CSV/JSON/Excel 共用已有链路。Vue、HTML、CSS、JSX、TSX 等尚不在本轮范围内。

Java 使用独立词法扫描，JS/TS 使用 Lezer JavaScript 对应语言模式划分语法区域。发现未闭合内容或解析恢复时保留可识别区域的行统计并警告，不把它作为完整编译器语法验证。C/C++/Python 分析器本轮不重写。

统计核心使用“从前往后读，并记住当前处于字符串还是注释中”的方法。它不执行代码，也不是完整编译器。复杂 Python f-string 内部表达式、C/C++ 所有预处理和翻译阶段细节尚未完整覆盖，不能承诺等同于编译器解析。

将来扩展语言时，需要先给出典型和边界样例，再在页面列为正式支持。只增加一个文件后缀，不代表真正支持了这个语言。

### 3.4 输入和异常处理

2026-11-05 补充已实现行为：读取和分析分别显示完成数、百分比及当前文件；读取可中止原生 FileReader 并停止后续文件，取消／迟到结果不保存为新快照。完成后展示成功、失败、跳过数量，失败文件不计入合计；文件表按 50 行继续加载。行解析提示恢复展示可获取的行列范围，编码／读取失败按文件报告；不把恢复位置等同源码错误，也不承诺所有解析提示均不影响行分类。解析器兼容性修复继续暂缓，函数专属提示仍隐藏。

报表使用按需创建的独立 Worker 生成，期间可继续操作列表；Excel 缓冲区转移回页面后发起下载，实际文件位置由浏览器设置决定。网站无法读取系统下载目录，本次验收的实际路径见 QUALITY.md。

2026-11-04 第一阶段优化：默认严格 UTF-8；文件输入可显式选择“UTF-8 优先，失败按 GBK”或“GBK（全部候选文件）”。GBK 解码标记在文件说明及导出中，不修改原文件。需要转换时，在编辑器中以原编码打开、核对中文并另存为 UTF-8，再选择 UTF-8 重试。读取失败、解码失败与二进制空字符分别报告；含空字符的内容不建议转编码。

单文件或粘贴文本上限约 5 MB；候选源文件总量约 40 MB、最多 5000 个。候选口径统一为排除目录、支持后缀筛选、相对路径去重后的文件，预览与读取限额共用同一集合。不支持文件在读取和限额之前直接跳过；重复候选路径保留首份，其他列出失败。实现中的容量按 1024 × 1024 字节计算。

新增 `.pyi` 使用 Python 行分类，单列“Python 类型声明”，默认计入总量，接入语言筛选、汇总、图表、历史和三种导出；不新增函数统计。行规则为 `physical-lines-1.2`，编码策略写入配置；旧快照保持原值，不与不同规则／配置直接比较净变化。JSON 报表结构仍为 schemaVersion 2，数据库结构不变。

默认排除 `.git`、`node_modules`、`dist`、`build`、`__pycache__`、`.venv`。目前是按目录名匹配，不是完整的 `.gitignore` 规则。用户可以调整排除项。

| 遇到的情况 | 应怎样告诉用户 |
| --- | --- |
| 编码无法读取、二进制内容、不支持的语言 | 在文件明细中标明失败或跳过及原因，不能悄悄消失 |
| 相对路径重复 | 当前保留第一份，其余显示路径冲突；不是按内容去重 |
| 部分文件失败 | 展示成功部分，同时显眼提示本次结果不完整 |
| 一个文件也没成功 | 不计为成功活动，保留问题清单 |
| 统计线程失败 | 显示错误和重试办法；旧结果要明确注明 |
| 保存历史失败 | 已完成的统计仍可查看和导出，不能说成统计失败 |
| 用户取消 | 不产生成功快照；保存已开始时的取消规则要明确 |

当前已有多数错误处理，真实 Python 文件已由用户确认正常。后续可讨论把“部分成功”和“统计失败”的视觉状态做得更醒目，避免只看总数时漏掉问题。

### 3.5 总量和时间范围

2026-11-10 展示调整：页面移除“区间净变化”和页脚规则编号。下文的历史比较思路不代表已有比较页面；统计规则版本仍保留在历史和导出中，不重算旧记录。项目介绍改为简短的功能、结果范围与统计口径说明。

2026-11-07 确认并实现：历史“查看结果”进入独立结果页，只保留 OVERVIEW（原总览数字与语言分布）和 FILES，不显示全局导航、大标题、项目／时间筛选、输入区、热力图或区间比较。该页持有所选快照副本，数字、饼图和导出始终对应同一快照；明细从 50 行起，“继续展开”每次加 50，文件名／路径搜索覆盖全部条目。返回历史不改变工作台输入或当前结果，后台新扫描完成也不替换该结果页。

工作台的大数字表示当前展示快照的规模。时间筛选包括最近 7、30、365 天和自选日期，自选最多 366 天。日期结束当天应包含在内。

历史列表和活动方块按选定范围筛选。当前实现会寻找截止时间之前最近的一次快照，哪怕它早于区间开始时间，因此它的准确含义是“截至该时间最近已知的规模”。设计上需要把快照时间放在总数旁边，不能让人误以为这个总数只属于本周新写的代码。

当前比较检查了项目和统计配置，但还没有充分证明两次扫描的是同一份范围。例如同一项目里先只扫一个文件，再扫整个文件夹，数字变大并不代表新写了这么多代码。这个问题应在扩展趋势分析之前补齐，具体方案见第 7 节。

**2026-10-21 确认的方块规则。** 按当前统计档案、所选日期范围内的快照计算：每天把每次成功保存扫描的有效代码行相加，重复扫描也累计。例如上午统计 100 行、晚上统计 120 行，当天为 220 行。它表示“当天统计过的代码量”，不能解读成新写了 220 行。

取所选区间最高的日合计为基准，比例 = 当天合计 / 区间最高日合计。最高值为最深色；其他非零值按 (0,25%]、(25%,50%]、(50%,75%]、(75%,100%] 分四档，0 为零档。切换时间范围后重新计算基准，区间外记录不参与峰值；全为 0 时全部为零档，不做除零运算。悬停或键盘聚焦显示当天累计行数、扫描次数和相对比例。

工作台总览和报表仍展示当前选中的单次快照，不因重复扫描而累加。工作台饼图默认展示当前快照；悬停、键盘聚焦或点击某一天后，展示当天每次已保存扫描的累计语言分布。重复扫描按相同方式累计，文件数量以“文件次”标注；无扫描日展示空分布。可点击“返回当前快照”，切换统计档案或日期范围时也恢复快照分布。未保存结果、取消任务不进入方块；删除快照会相应减少当日合计并重新计算区间深浅。

**日历展示。** 按月份分组并留出间隔，顶部标注月份，左侧按周一至周日对齐并标注周一、周三、周五、周日。每个日期只出现一次，范围首尾月份只展示范围内日期；年视图空间不足时在日历内横向滚动，不挤压整个页面。左下角“我们是怎样统计的”直达项目介绍中的活动统计文章，说明累计、重复扫描、相对深浅和分布联动。

### 3.6 输出字段与报表

2026-10-21 用户确认本轮实现以下字段，按语言汇总当前快照中的成功源文件。支持语言仍为 C、C++、Python，不照搬参考图片中的 Java 或 C#。

| 输出字段 | 定义 |
| --- | --- |
| 语言 | 成功文件归属的语言 |
| 源文件数 | 成功统计的文件数，包含空文件 |
| 代码行数 | 有效物理代码行之和，包含混合行 |
| 空行数 | 空行之和 |
| 注释行数 | 纯注释行之和，不重复累计混合行 |
| 函数个数 | 源文本中有函数体的命名函数定义数之和 |
| 最大值／最小值 | 各成功源文件有效代码行数的最大值／最小值 |
| 均值 | 有效代码行总和 / 成功源文件数 |
| 中位数 | 将各文件有效代码行数排序后取中间值；偶数样本取中间两项的平均值 |

项目合计使用全部成功文件重新计算分布，不对各语言的均值或中位数再次平均。空文件以 0 行参与分布；没有成功文件时，文件数和行数合计为 0，分布值为空。页面最多显示两位小数，导出保留计算值。失败和跳过文件保留在明细中，不进入汇总样本。

**函数定义规则。** 使用 Lezer 的 C++／Python 语法解析器，C 按 C++ 语法的基础子集解析。Python 包含普通函数、async 函数、类方法和嵌套定义；C/C++ 包含有函数体的普通函数、成员函数、构造／析构函数和运算符重载。不计调用、原型声明、默认／删除声明及 lambda。不执行源码，不展开宏或消除条件编译分支，因此不是编译后实际存在的函数数。解析器依据：[C++ 语法](https://github.com/lezer-parser/cpp)、[Python 语法](https://github.com/lezer-parser/python)。

语法树有错误恢复节点、解析失败或旧快照没有函数字段时，该文件函数数不可用，仍保留物理行统计及警告。语言或项目范围中只要有一个成功文件的函数数不可用，对应函数合计也不可用，不把已知部分当作完整合计。函数规则版本独立保存为 `function-definitions-1.0`；2026-10-21 的物理行规则为 `physical-lines-1.0`，不伪造旧历史缺失值。

2026-10-28 用户先决定保留现有函数功能，随后确认暂缓页面展示：语言汇总和文件明细隐藏函数列，项目介绍移除函数说明，页面隐藏函数专属警告，并于 2026-10-29 补充隐藏通用行解析说明，异常筛选同步；其他具体警告保留。底层算法、历史数据和导出字段保持原样，上表的函数字段仍用于导出。匿名函数等未决问题与恢复展示前的考虑记录于 `docs/hesitate.md`，没有自动批准新口径。Java、JavaScript、TypeScript 暂不统计函数，JSON 使用 null，CSV／Excel 使用 —，不当作 0。行规则更新为 `physical-lines-1.1`：新增语言使旧扫描中曾被跳过的文件进入总量，所以不直接比较新旧规则净变化；已有历史结果保留。

CSV、JSON、Excel（.xlsx）均导出语言汇总、文件明细和统计说明。JSON 报表版本升级为 2，保留 snapshot，并增加 summary 和 definitions；JSON 缺失值为 null，CSV/Excel 为 —。Excel 包含“语言汇总”“文件明细”“统计说明”三个工作表。只导出统计信息，不保存或导出源码正文；报表暂不是历史恢复导入格式。

## 4 前端页面怎么组织

整体保留等宽英文标题、清楚的中文正文、细边框和留白。我们已经移除了参考 PPT 里的二进制插图，它不是产品功能。顶部缓慢移动的文字条可以保留；系统要求减少动态效果时应停止动画。

主题只保留原色与暗色。原色为米白底、深色内容；暗色为深炭底、不同深浅的米白内容。图表、下拉菜单、输入框、按钮和提示都跟随主题，不单独更换方块颜色。异常信息除了颜色还要有文字，图表也要有数量和标签。

### 4.1 导航和页面职责

下一版顶部导航为：

```text
code / meter       工作台    扫描历史    项目介绍       原色／暗色
```

| 页面 | 使用者来这里做什么 | 应保留的主要控件 |
| --- | --- | --- |
| 工作台 | 导入代码、查看本次结果和规模分布 | 项目选择、新建项目、时间筛选、输入与统计 |
| 扫描历史 | 找到某一次记录、查看或删除 | 项目选择、时间筛选、历史记录 |
| 项目介绍 | 了解用途、统计规则、设计和搭建方式 | 页面内目录、开始使用、查看源码等入口 |

2026-10-21 已确认并实现：“统计口径”更名为“项目介绍”；介绍页隐藏整个项目／时间筛选栏，扫描历史只保留项目和时间筛选，新建统计档案只在工作台出现。项目介绍使用左侧可展开目录和右侧文章，初始分组为功能介绍、设计思路、统计方式。输入、按钮和文件投放区域沿用工具栏的 4px 圆角，活动方块保留方形。

### 4.2 工作台

电脑浏览器中保持“左边输入，右边总览”，下面是语言分布、活动和文件明细。宽表只在自己的区域内横向滚动。

五个功能板块只保留 INPUT、OVERVIEW、COMPOSITION、ACTIVITY、FILES 英文标题，去掉原中文标题；按钮、字段、异常与必要单位仍保留中文。总览保留总物理行等式，去掉第二行解释。板块功能的完整说明留待项目介绍统一完善。

输入区提供文件和文本两个入口。选择文件后能看见文件名并移除；文本区保留语言、示例和清空按钮。开始统计后显示正在读取、分析还是保存，避免只有一个一直转的图标。

结果区除了数字，还应说明“本次结果”“历史快照”或“本次失败后保留的上次结果”。总数旁显示成功、失败、跳过的文件数。无数据时给出下一步操作，不用一个孤立的 0 让人猜。

语言饼图旁保留明细，保证不用辨认颜色也能看懂。活动格在悬停、点击或键盘聚焦时显示日期和次数，并联动当天累计的语言分布。文件表支持搜索、排序和只看问题文件。

### 4.3 扫描历史

一条历史记录至少让人认出：哪个项目、什么时候扫描、多少有效代码、几个成功文件、是否有失败文件。查看后要明确表示正在看旧快照。

删除要确认，并解释这条记录对应的活动也会减少。首版历史按用户操作删除；尚没有自动清理策略。将来加入“保留最近 N 次”等选项时，应先有可靠备份和恢复功能。

### 4.4 项目介绍

这个页面既面向第一次使用的人，也面向想了解课程项目如何完成的人。先介绍能解决什么问题，再解释结果，最后介绍技术实现。技术部分放在后面，阅读顺序更自然。

2026-10-21 已确认并实现左侧可展开目录，点击小节在右侧阅读文章。当前分组与内容：

- **功能介绍**：从一份代码开始、统计档案与扫描历史、统计结果与报表导出。
- **设计思路**：在浏览器中处理代码、让页面与统计规则分别维护。
- **统计方式**：代码行／空行／注释行、各支持语言的差异、文件行数分布、活动方块与当天累计语言分布；函数说明目前隐藏。活动文章包含 100 行 + 120 行 = 220 行的示例。

文章内容位于 `src/content/introduction.ts`，后续可继续按已确认功能增补。日历说明入口直接打开活动文章、展开对应目录并聚焦文章标题。

以下为此前讨论的内容方向与草图，不是本轮全部实现的要求；开始统计、查看源码等额外入口仍待决定：

1. **这个工具能帮你什么**：看项目规模、语言分布和扫描记录；放一个“开始统计”按钮。

## 6 不同的人可能更关心什么

下面是需求假设和讨论建议，不是用户调研结论。一个人可能同时刷题、使用 AI 编程和做科研，因此不急着在首页强制选择身份。先用统一工作台，哪类需求被证实有用，再增加可选视图。

### 6.1 使用 AI 辅助编程的人

**可能的问题。** “AI 帮我写了一堆代码，项目能运行，但我不知道多出来的文件各自做什么，哪些内容重复了。”对这类人，知道 2000 行还是 3000 行可能只是第一步，更有价值的是找到值得检查的地方。

**可以讨论的结果。** 按目录看代码分布、列出较大的文件、提示内容完全相同的文件、给快照加“新增登录页”等备注。它们帮助用户定位，而不直接宣布某个文件应该删掉。

**需要纠正的期待。** 代码长不等于冗余；短代码也可能有重复逻辑。仅看源文件无法可靠判断某段代码是否由 AI 写出。相似代码可能来自合理模板，未发现静态引用也不一定意味着无用，例如动态加载或框架约定。

“AI 冗余率”暂不进入指标列表。若以后有重复检测，应展示重复片段、比较方法和排除规则，名称用“疑似重复”更合适。AI 来源如果要记录，应由用户标记，并保留“未知”。

**先验证什么。** 让使用者导入一个真实项目，请他指出最想整理的地方，再看文件大小排序、目录分布和重复提示是否能帮助他作出下一步决定。判断有效与否，看是否找到了有用线索，而不是图表是否增加。

### 6.2 算法刷题的人

**可能的问题。** “这个月用 Python 和 C++ 分别练了什么？哪种题型经常卡住？哪些题需要再做一次？”这里的“练习量”更接近题目数、练习次数和复习情况。

语言代码行占比仍有参考作用，但不能代替做题数量。同一道题写两个版本不该算成两道不同题；同一个文件扫描五次也不代表练了五次；代码短不能证明理解更好。

**日志想法。** 让用户记录题目或项目名称、题目链接、语言、算法标签、练习日期、结果和一句复盘。可以关联一次扫描，但练习记录有自己的编号。结果如果来自本人填写，要明确标为“自记结果”，不能伪装成平台判题结论。

**插件是否必要。** 先试网页手动记录。只有当“总忘记打开网页”或“填写文件路径太麻烦”成为真实障碍，再考虑 VS Code 插件。编辑器里的文件保存事件不能自动等同于一次完成的练习。

**先验证什么。** 让成员连续使用一周的简单日志，观察记录是否负担太重、复盘时是否真会查看语言和题型分布。先关心有没有帮助回顾，而不是先做复杂打卡。

### 6.3 工程项目管理的人

**可能的问题。** “这次交付包含哪些模块？哪些目录变化大？本次报告有没有漏扫？比较的是同一范围吗？”对小团队负责人，报告的完整性和可追溯性可能比一个总数更重要。

可讨论的内容包括目录规模、业务代码与测试代码的分布、扫描范围、排除项、版本备注和前后快照差异。项目角色分类最好由成员确认；目录叫 `test` 是一个线索，不保证里面全是测试。

工程中的生产力不宜由一个活动指标代表。SPACE 研究强调开发者生产力有多个维度，不能用单一指标完整衡量。因此，这个工具可以提供规模信息，但不据此排名个人产出。[参考 S1](https://www.microsoft.com/en-us/research/publication/the-space-of-developer-productivity-theres-more-to-it-than-you-think/)

**先验证什么。** 请一位项目负责人指出交付前必须检查的三个信息，再拿一份导出报表给他使用，确认哪些字段缺失。联网读取 GitHub、持续集成和多人权限可以以后再评估。

### 6.4 做科研的人

**可能的问题。** “这张图用的是哪一版代码？哪个脚本负责清洗数据？这次改动和哪次实验有关？”不同学科差异很大，下面更适合使用脚本、Notebook 或计算实验的小组，不代表所有科研工作。

关于科研计算的实践文章强调组织项目、记录步骤和追踪变更的重要性。这为我们考虑“帮助未来的自己理解项目”提供了依据，不能据此认定科研人员都需要一个代码行统计工具。[参考 S2](https://journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1005510)

**可以讨论的最小功能。** 为扫描快照添加实验名称、代码版本、脚本用途、环境说明位置和结果链接。让统计成为实验记录的一份附件，而不是让代码行数表示科研成果。

如果涉及机器学习，现有 MLflow 已提供参数、代码版本、指标和产物的跟踪能力。这说明完整实验跟踪需要的数据远多于代码行数；本项目可以先关联已有实验记录，不急着重做一套平台。[参考 S3](https://www.mlflow.org/docs/latest/tracking/)

**需要确认的边界。** Notebook 应只提取代码单元，排除输出、图片和 Markdown；当前还不支持 `.ipynb`。只保存代码快照也不能证明实验可复现，还需要数据、环境、参数、随机性和操作步骤。

**先验证什么。** 用一个公开、无敏感信息的科研示例项目，请使用者从一份结果找到对应的脚本和说明，观察哪些信息确实缺失。没有真实使用者前，这条路线先留在想法区。

## 7 实现方案和模块安排

这一节回答“如果决定做，怎样落地”。其中未实现内容都属于方案，不是当前功能承诺。

### 7.1 保持核心和界面分开

当前结构：

```text
apps/code-meter-web/src/
  core/          只接收文本，分析并计算结果
  platform/      读取文件、保存快照、导出和调度任务
  workers/       把分析放到后台线程
  components/    图表和选择器等界面组件
  pages/         工作台、历史和现有规则说明页面
  composables/   扫描、历史、项目和主题管理
  utils/         共用格式化函数
  assets/        主题和布局样式
  App.vue        导航与共享状态协调
```

后台线程，也就是 Web Worker，作用是让分析工作尽量不挡住页面操作。核心分析器不应依赖 Vue、浏览器数据库或插件接口，这样以后换成桌面文件读取方式，统计规则仍能复用。

2026 年 10 月 20 日已把 `App.vue` 拆成工作台、历史和规则说明三个页面组件，并把扫描流程、历史管理、项目设置和主题设置提取为组合函数。组合函数可以理解为“把一组相关操作装起来”，页面调用它，不必知道每一步细节。2026 年 10 月 21 日继续在独立介绍页面中实现目录和文章，内容与页面分开维护。

原先规划的 `packages/code-core`、`packages/platform-browser`、`packages/ui` 目前尚未落地。先整理稳定接口，再逐步迁移；只把确有复用价值的代码放进共享包，不为了目录好看制造很多空包。核心不反向调用页面。

项目介绍沿用独立页面组件，现有三组目录包含功能介绍、设计思路和统计方式，保留能力边界与规则例子。工作台和历史页显示筛选栏，历史隐藏新建，介绍页隐藏筛选栏。后续是否改成独立网址仍待讨论。

### 7.2 扩展语言和统计维度

对应 I01、I02。每个语言分析器接收统一的文本输入，返回相同格式的文件结果。Java、JavaScript、TypeScript 已于 2026-10-28 接入该接口；今后新增 Go 等其他语言时，主要修改分析器注册和样例，不让图表、存储到处增加语言判断。

当前接口已经有分析器注册入口。下一步需要明确注释和字符串规则、支持范围、错误结构和规则版本。每种语言至少覆盖空文件、不同换行、行尾注释、字符串里的注释符号、多行内容和不完整输入。

以后如果增加逻辑语句数，应另列指标和定义。例如 Python 的跨行表达式与 C++ 的分号并不是一套简单替换规则。复杂度、重复度也各自保留含义，不合并成未经验证的跨语言公平系数。

### 7.3 让历史比较更可靠

对应 I03、I09。给快照补充“这次扫了什么”的说明，例如输入类型、文件夹范围说明、配置、是否部分失败和用户备注。文件数和路径清单可帮助检查范围，但不能仅因文件数变化就判断不可比，因为项目可能正常新增文件。

建议让用户为固定扫描范围建立名称，例如“完整仓库”和“算法练习目录”。全项目和单段文本默认不自动比较。部分文件读取失败时，净变化标为不完整或不可比较；缺少基线继续显示原因，不能填 0。

当前只保存汇总和文件结果，所以只能做规模净变化。若要展示真正新增、删除或修改的代码行，需要额外的 Git 差异数据或文本版本，不能从两个总数反推。默认不增加源代码正文存储。

活动图将来若支持扫描、练习或实验记录，必须有明确的数据类型和图例，分别统计。不能把旧的扫描次数直接改名为练习次数。

### 7.4 给 AI 编程场景提供整理线索

对应 I07。可先做两项低成本试验：按相对目录汇总规模，以及用内容摘要识别字节内容完全相同的文件。摘要相当于文件指纹；分组后仍应复核内容，并把“完全重复”与“语法相似”分开说明。

完全重复只能说明内容相同，不能直接说明应该删除。配置、生成文件、依赖和样例要单独识别或排除。相似函数、无用代码、依赖关系和复杂度需要更深入的语言解析，等有真实需求再评估成本。

结果以“建议检查的文件列表”呈现，附路径、理由和证据。首版不自动删除或重构代码，也不引入无法解释的 AI 检测分数。当前行统计、规模快照继续独立工作。

### 7.5 先做独立的日志模块

对应 I05、I08。建议先有一个通用记录结构，再按场景补字段：

| 记录 | 必需信息 | 关系和说明 |
| --- | --- | --- |
| 扫描快照 | 编号、项目、扫描时间、规则、范围、文件结果 | 说明当时看到的代码规模 |
| 练习记录 | 编号、题目标识、日期、语言、自记结果 | 可以关联快照；不要求每次记录都扫描 |
| 补充信息 | 标签、复盘、题目链接、练习用时 | 用时注明手填或计时；不能从扫描时间推断 |

题目标识可以由“平台加题号”或自定义名称确定。不同题目数按题目标识去重，练习次数按记录编号计数；同一题的复习和多语言解法可以保留多条记录。

新增记录前要设计本地数据结构版本、校验、备份导入和升级流程，避免以后改字段后旧历史读不出来。当前数据库版本和导出文件版本不是完整的数据迁移方案，需要补齐。

如果网页日志被证明有用，再考虑 VS Code 插件：由用户主动触发，把选中的文件分析结果和日志信息传给同一套核心。网页版与插件的存储不能假定自动互通，需要明确的文件交换或后端同步方案；当前不搭后端。

### 7.6 给科研记录留一个轻量入口

对应 I10。先允许给快照附加实验名称、代码版本、数据版本说明、环境说明链接和结果链接。这些字段由用户提供，不自动声称已验证可复现。

Notebook 支持应单独作为解析适配器：读取文档结构、选择代码单元、保留单元定位、跳过输出，检查语言信息和损坏文件。不能把整个 Notebook 的 JSON 文本直接当作 Python 行数。

文件扫描只读取本次授权的材料，不执行实验、不读取链接中的数据集，也不自动上传科研文件。团队确实需要跨设备协作时，再讨论权限、服务器和保存周期。

## 8 接下来怎样推进

建议先完成共同基础，再只选一个场景做试验。两个人同时展开 AI 整理、刷题插件和科研跟踪，容易让每部分都停在半成品。

| 阶段 | 具体工作 | 看得见的完成结果 |
| --- | --- | --- |
| 先稳定基础 | Python 原文件已由用户确认正常；后续讨论范围可比性和部分失败提示 | 能解释每次结果，失败不会被误认为成功 |
| 整理页面和文档 | 页面拆分与说明同步已完成；介绍页已有三组目录和文章 | 页面职责清楚；后续按确认的内容完善介绍页 |
| 补主要语言 | 已新增 Java/JavaScript/TypeScript 行统计；其他语言按后续需求确认 | 新增语言不改汇总与存储主流程 |
| 选一个小试验 | 在目录整理和手动练习日志中选一个 | 用真实任务验证是否有帮助 |
| 再评估扩展 | 相似代码、插件、Notebook 或实验关联 | 有明确使用者、数据来源和验收条件后再开发 |

可采用的分工是：一位负责统计核心、数据结构与规则测试；另一位负责页面、交互与展示。每个功能在开始前共同确认一个输入例子和预期结果，集成时交换检查。

### 8.1 下一版至少要这样验收

- 同一份文件的总行数能够人工复核，文件汇总和项目汇总一致。
- 换行、字符串、注释和异常文件都有样例，声明支持的语言都有对应测试。
- 同样的代码重复扫描不累加项目规模；无基线、范围不同和部分失败有明确说明。
- 文本清空后可以继续粘贴，结果和历史不会被顺带删除。
- 原色和暗色下，正文、菜单、图表和键盘焦点都清楚。
- 项目介绍能让第一次使用的人说清楚：这个工具做什么、数字是什么意思、代码保存在哪里。
- 如果加入日志，同题多次练习与不同题目数分开统计，自记结果不会标成自动判题结果。
- 如果加入整理提示，用户能看到证据；文件长或重复不能直接导致删除建议。

### 8.2 仍需要共同决定的问题

介绍页已隐藏筛选栏，并实现功能介绍、设计思路、统计方式三组目录；具体文案可继续调整。新场景中先验证哪一个、需要支持哪些额外语言、是否接受手动记录，以及什么时候需要插件，都还没有定死。

文档也要像代码一样检查版本。本文件继续维护在 `docs/代码统计项目设计说明_V0.2.md`，后续按“新增想法—作出选择—补实现方案—更新验收”的顺序维护，不把所有讨论直接变成待开发任务。
